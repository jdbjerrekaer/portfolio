## Recruiter takeaway

This is a judgement story, not an automation story.

The agent reads my shopping list, finds the best current supermarket offer across seven Danish chains, and writes the answer back into the list I already use. Most of the work went into restraint: which native field each piece of information belongs in, and when the correct output is nothing at all.

What this proves:

- I design into surfaces people already use instead of asking them to adopt a new one
- I treat "the system declines to answer" as a designed state rather than a failure
- I can take a project from research through to unattended production on real hardware
- I verify what I ship, including reading back every write before reporting success

## The problem

**Comparing offers by hand is work nobody actually does.**

Danish supermarkets rotate weekly offers across seven chains near me. Checking whether something on my list is cheap this week means opening an offers app, searching each item, and dividing pack prices down to per unit prices so a 24 pack can be compared with a 6 pack.

Nobody does that. I did not either, so I quietly overpaid for years.

The price lookup turned out to be the easy part, roughly one API call. The work went into where the answer should appear, how sure it has to be before it speaks, and when saying nothing is the correct output.

## Designing for a surface that already exists

**The best interface here was one I did not have to build.**

The obvious build is an app with a list, a price column and a store filter. I did not build that. I would have to remember to open it, and once I have to remember something, the tool has already failed.

So the agent writes into the Apple Reminders list I use anyway. Nothing new to install, nothing new to open. If the agent dies I still have a working shopping list.

This is a desire path with a twist. Normally you watch where people wear the grass down, then pave that. Here the path was already paved. The move was refusing to lay a second one next to it and hoping traffic would switch. Every product that opens with "install my app first" is a fresh path through the grass, asking people to change route for the maker's convenience.

That decision set the real constraint. I was not designing a screen. I was designing into three fields Apple already gives every reminder, and each one had to earn its place.

**Note.** Pack size, price, price per unit, product name. This is the part you actually compare.

**Location.** The store, as a real geofence rather than as text.

**Due date.** The day the offer expires, so the list sorts itself by what runs out first.

Location does the most work here, and it is the clearest case of calm technology in the project. Weiser and Brown's idea is that a tool should sit in the periphery and move to the centre only when it becomes relevant. The reminder stays quiet for six days, then appears as I walk into the shop. Attention is the scarce resource, and the geofence spends none of it until it can be useful.

An early version put the store name into the note as text. It looked fine and it was wrong. A store is a place, and Reminders has a place field. Writing "Bilka" into a note is a picture of the right answer instead of the answer. Fixing it meant dropping to EventKit, because AppleScript does not expose a location property on reminders at all.

The same reasoning retired "til 06/08" from the note. An expiry is a due date, not prose. Once it is a due date, the list reorders itself around whatever expires soonest and I do nothing.

## The constraint that shaped everything

**macOS security rules decided the architecture before I did.**

The agent runs on a Linux box. The list lives on a Mac. macOS TCC guards Reminders access and keys it to the responsible process, and over SSH that process is sshd, which is denied. Root does not help, because TCC is enforced above uid 0. I spent real time confirming that no privilege escalation would work, because a fix that does not exist is the most expensive thing to keep looking for.

So I inverted the dependency. The Linux side never asks the Mac for anything. A LaunchAgent inside the Mac's GUI session, where the grant actually lives, dumps the list to a file and applies a queue file. Two plain text files are the whole interface between the machines.

The constraint made the design better. A file drop has no session to expire and no socket to drop, and either machine can restart without the other noticing.

It also produced the most useful lesson. The bridge between the machines looked flaky, with 299 restarts in the log. It was not flaky. The library calls connect() on one shared server object per client, so the second concurrent client throws, and that exception was unhandled inside an async Express handler, which kills the process. My own enricher was the fatal second client.

I patched it to refuse politely instead of dying. That immediately exposed a second bug hiding behind the first. The library also overwrites the SDK's close handler, so the transport was never released and every later client got refused forever. A crash loop had become a permanent lockout, which is worse. Both needed fixing, and either one alone leaves it broken.

Housekeeping turned out to matter too. The list had grown to 686 entries, mostly completed items nobody had cleared, and Apple's own scripting layer slows to a crawl at that size. A small EventKit tool now deletes anything completed more than a week ago, once a day. It runs dry by default, and it refuses to touch an item whose completion date is missing, because unknown age is not the same as old.

## Teaching it what I actually mean

**Two similar sounding rules turned out to need opposite behaviour.**

"Sodavand" on my list means 33 cl cans. Never bottles. A naive version scales a per litre price by 0.33 and happily matches a 1.5 L bottle. The arithmetic is correct and the recommendation is nonsense. The agent now requires the offer's real packaging to match before it computes anything.

The next distinctions were subtler, and each turned out to be a different kind of rule.

**Juice.** I want real orange juice, not nectar and not from concentrate. No data source carries that distinction, because offer descriptions are marketing copy. A keyword filter on "koncentrat" would match nothing and pass everything, while looking like it worked. So the rule is positive evidence only, and it fails closed: an offer has to prove it qualifies. Most weeks nothing does and the list stays empty. That is the intended behaviour, not a gap.

**Yoghurt.** I prefer pære og banan. That is a preference, not a requirement. Matching offers rank first, and when none exist it falls back to the cheapest. Getting no yoghurt at all because this week's offers are strawberry would be worse than useless.

"I want X" and "I prefer X" are different data structures. Collapsing them into one filter breaks both.

## Knowing when to say nothing

**The worst failure was a correct answer.**

The sharpest bug was not a crash. The agent recommended a yoghurt offer at 18 kr/kg. Real offer, current, correctly parsed. It was also half as much again as the same product's everyday shelf price of 11.95 kr/kg.

A tool that only reads the offers feed cannot see this. It will send you across town to overpay, and every number on the screen is accurate.

Offers now have to beat a known everyday price before they are worth mentioning. When they do not, the note says so and points at the shelf price instead.

The name for this risk is automation bias: people over-trust output that looks computed. A number I would have questioned from a person, I accepted from my own tool. That is what makes a confident, accurate, wrong answer worse than no answer at all. Deciding when the system declines to speak is trust calibration, and it is the part of this project I would defend first.

Verification is a feature. Every helper here reads back what it wrote before reporting success, because a geofence at (0,0) and a geofence at Bilka look identical to the code that wrote them.

## Two more places it was quietly wrong

**A typo skipped every rule I had written.**

Correction started as a lookup table of known variants. It only ran when a
search came back empty, which sounded reasonable and was the wrong trigger. The
offers API does its own fuzzy matching, so "sodavnd" returned plenty of offers.
It just did not match the rules, which are keyed on the correct spelling, so
the 33 cl packaging rule never ran and a 1.5 litre bottle won.

Correction now fires whenever the typed name matches nothing I have rules for,
not when the search comes back empty, and it fires before the gates rather than
after. The dictionary is the one already on the Mac, so it needs no service and
no key, and it only suggests a correction for words it also flags as wrong.

The first version of that also fixed the wrong word. "Pære" was corrected to
"ærter" because peas are stocked this week and pears are not, so peas scored
better. Being productive is not the same as being plausible. A typo rarely
changes the first letter, so candidates now have to keep it. The failing case
is a permanent test.

**An annotation was true when written and nobody checked it since.**

The only signal for "this item needs pricing" is an empty note, so an annotated
item was never looked at again. Offers rotate weekly. An item kept last week's
price, last week's shop and a due date in the past, and the geofence still
fired.

Once a day, anything whose offer has expired has its note cleared, which hands
it back to the normal path to be re-priced. Everyday shelf prices carry no
expiry and are left alone.

Both of these are the same failure as the yoghurt: not a crash, not an error
message, just a confident answer nobody re-checked.

## What I would do next

**Three gaps I know about, in the order they bother me.**

- The shelf price baseline is hand entered. It should come from the shelf price APIs the tool already talks to.
- The geofence for the shop directly below my flat fires every time I come home. Correct code, wrong for one real case.
- The Mac finds the Linux box by an address its router hands out. If that address changes, the ten second path goes quiet and the half hourly fallback takes over without telling anyone. Degrading silently is the part I do not like.

The code is one repo across two machines. The live paths are symlinked into it, so editing the repo edits production, and a deploy script handles the half that cannot be symlinked.
