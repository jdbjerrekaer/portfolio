## The problem {#problem}

Danish supermarkets rotate weekly offers across seven chains near me. Checking
whether the thing on my shopping list is cheap this week means opening an
offers app, searching each item, and mentally dividing pack prices into
per-unit prices to compare a 24-pack against a 6-pack.

Nobody does that. I didn't either. So I overpaid, quietly, forever.

The interesting part of this project isn't the price lookup — that's an API
call. It's everything around it: where the answer should appear, how much
confidence it needs before it speaks, and when the right answer is nothing at
all.

## Designing for a surface that already exists {#surface}

The obvious build is an app: a list, a price column, a store filter. I didn't
build that, because I'd have to remember to open it — and the moment I have to
remember something, the tool has failed at the only job that matters.

Instead the agent writes into the Apple Reminders list I *already* use. Nothing
new to install, nothing new to open, and it degrades gracefully: if the agent
is down, I still have my shopping list.

That decision set the real design constraint. I wasn't designing a screen — I
was designing into three fields Apple gave me, and each one had to earn its
place:

| field | carries | why |
|---|---|---|
| **note** | pack size, price, per-unit price, product | the thing you compare |
| **location** | the store, as a real geofence | fires when you're there |
| **due date** | the day the offer expires | the list sorts itself by urgency |

An early version put the store name in the note as text. It looked fine and it
was wrong — a store is a *place*, and Reminders has a place field. Writing
"Bilka" into a text note is a screenshot of the right answer rather than the
answer. Fixing it meant dropping to EventKit, since AppleScript doesn't expose
a location property on reminders at all.

Same reasoning retired "til 06/08" from the note. An expiry isn't prose, it's a
due date — and once it's a due date, the list re-sorts itself around what
expires soonest without me doing anything.

## The constraint that shaped everything {#constraint}

The agent runs on a Linux box. The list lives on a Mac. macOS **TCC** guards
Reminders access and keys it to the *responsible process* — over SSH that's
`sshd`, which is denied. Root doesn't help; TCC is enforced above uid 0. I
spent real time confirming there was no privilege escalation that would work,
because the fix that doesn't exist is the most expensive thing to keep looking
for.

So I inverted the dependency. The Linux side never asks the Mac for anything.
A LaunchAgent inside the Mac's GUI session — where the grant actually lives —
dumps the list to a file and applies a queue file. Two plain TSV files are the
entire interface between the machines.

The constraint made the design better. File-drop has no session to expire, no
socket to drop, and either side can be restarted without the other noticing.

It also produced the session's most useful lesson. The MCP bridge between the
machines was "flaky" — 299 restarts logged. It wasn't flaky. `supergateway`
calls `server.connect()` on one shared server object per connection, so the
*second* concurrent client throws, and unhandled inside an async Express
handler, that kills the process. My own enricher was the fatal second client.

I patched it to refuse politely instead of dying — and that immediately exposed
a second bug hiding behind the first: the library overwrites the SDK's
`onclose` handler, so the transport was never released and every later client
got refused forever. A crash loop had become a permanent lockout, which is
worse. Both needed fixing; either alone is broken.

## Teaching it what I actually mean {#meaning}

"Sodavand" on my list means 33 cl cans. Never bottles. A naive implementation
scales a per-litre price by 0.33 and cheerfully matches a 1.5 L bottle — the
arithmetic is right and the recommendation is nonsense. The agent now requires
the offer's actual packaging to match before it computes anything.

Then the distinctions got subtler, and each one turned out to be a different
*kind* of rule:

**Juice** — I want real orange juice, not nectar, not from concentrate. No data
source carries that distinction; offer descriptions are marketing copy. A
keyword filter on "koncentrat" would match nothing and pass everything, looking
like it worked. So the rule is positive-evidence-only and fails closed: an
offer must *prove* it qualifies. Most weeks nothing does, and the list stays
clean. That's the correct behaviour, not a gap.

**Yoghurt** — I prefer pære og banan. That's a preference, not a requirement.
It ranks matching offers first and falls back to the cheapest when none exist.
Getting no yoghurt because this week's offers are strawberry would be worse
than useless.

The design lesson is that "I want X" and "I prefer X" are different data
structures, and collapsing them into one filter breaks both.

## Knowing when to say nothing {#silence}

The sharpest failure I found wasn't a crash. The agent recommended a yoghurt
offer at 18 kr/kg — a real, current, correctly-parsed offer. It was also a
third *more expensive* than the same product's everyday shelf price.

A deals tool that only reads the deals feed cannot see this. It will confidently
route you across town to overpay, and every number it shows you is accurate.

So offers now have to beat a known everyday price before they're worth
mentioning. When they don't, the note says so and points at the shelf price
instead.

That's the thread running through the whole project: the hard part of an
assistant isn't producing an answer, it's having the judgement to withhold a
technically-correct one. Verification is a feature. Every helper here reads
back what it wrote before reporting success — because a geofence at (0,0) and a
geofence at Bilka look identical to the code that wrote them.

## What I'd do next {#next}

Honest gaps, in the order they bother me:

- The shelf-price baseline is hand-entered. It should come from the shelf-price
  APIs the tool already talks to.
- The store geofence for the shop directly below my flat fires every time I come
  home. Correct code, wrong for one real-world case.
- Spelling correction lives in the search layer, so a typo on the list fails
  before correction can run. It should self-heal instead of needing a rename.

The code is one repo across two machines, with the live paths symlinked into it
so editing the repo *is* editing production — and a `deploy.sh` for the half
that can't be symlinked.
